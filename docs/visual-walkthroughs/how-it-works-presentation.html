k8s-just-in-time-infra

Infrastructure does not outlive the applications that use it.

A proof of concept.

Databases, caches, anything an app declares it needs, created when it deploys and removed when it stops needing it, with enough delay to change your mind.

The premise

Infrastructure should be requested by the app, not by a person.

Self-service Catalogues made provisioning infrastructure fast. However, nothing connects a provisioning request to the application workload that needed it, so deleting the workload leaves the infrastructure running.

Our Demo App

An app asks for infrastructure in annotations.

For example: our demo voting app asks for infrastructure using the following annotations.

The split

A controller on K8s. A provisioner on Docker.

The controller decides

Watches annotations, works out what should exist and for how long, and wires the result back into the cluster.

Has no credentials. Cannot create anything itself.
one authenticated
HTTP call

The runner / provisioner builds

Takes the call, runs a versioned Terraform module against the Docker daemon here or a cloud API in production, and reports back what it made.

Knows nothing about namespaces, apps or expiry.
No polling

The pod waits, without anything waiting.

t0 CreateContainerConfigError The pod is scheduled. Its container needs a Secret to build an environment from, and that Secret does not exist, so the kubelet will not start it.
t1 Secret created The database is up. The controller writes its address and password into the namespace.
t2 Running The kubelet was already retrying. This attempt resolves the Secret and the container starts.

No init container, no probe against the database, no timeout to guess. The failure and the retry were already there.

What the app actually sees

A Secret, automatically created by the controller.

vote / worker

REDIS_URL + credentials

From Secret jit-redis, key service_url. The Service has no selector; an EndpointSlice points at the container IP.

worker / result

DATABASE_URL + credentials

From Secret jit-postgres. No hostname, port, user or password in the manifests or the code.

The app never hears about Docker, Terraform, or IPAM. That is the point of the split.

The centrepiece

Cleanup has two speeds.

soft delete

Delete the app, and a clock starts

The infrastructure keeps running. Redeploy inside the window and the clock is cleared: the database never went anywhere. Let it run out and it is destroyed, data and all.

hard delete

Delete the namespace, and it is gone

The clock is ignored. Deleting the entire infrastructure is a deliberate act in a way that deleting a Deployment is not.

Accidents get a grace period. Decisions do not.

What the controller keeps

The claim. Everything so far is a field on it.

kind: InfraClaim
metadata:
  name: voting-a-postgres
  ownerReferences: [ Namespace/voting-a ]
  finalizers:      [ jit.infra/destroy ]
status:
  phase:        Active
  referencedBy: [ worker, result ]
  expiresAt:    —

↓  all references removed (deployments deleted, namespace still exists) — clock starts

kind: InfraClaim
metadata:
  name: voting-a-postgres
  ownerReferences: [ Namespace/voting-a ]
  finalizers:      [ jit.infra/destroy ]
status:
  phase:        Orphaned
  referencedBy: []
  expiresAt:    2026-09-13T21:04:10Z
This is what ties the infrastructure to the app that asked for it. Nothing else in the system holds that link. ownerReferences names the namespace as its owner, so deleting the Deployment does not touch it, and deleting the namespace marks it for deletion too.
referencedBy is who is using it and expiresAt is the clock. The finalizer is what stops it being forgotten if a destroy fails.
The controller writes it. The runner never sees it. Nothing else in the cluster knows it exists.
How do we know the infrastructure is still needed

The annotation is either there, or it is not.

Every thirty seconds the controller walks every claim, lists the Deployments in its namespace, and checks whether any still carry the annotation. Then it updates the referencedBy on the claim.

referencedBy: [ vote, worker ] Ready
vote is deleted
referencedBy: [ worker ] still Ready
worker is deleted
referencedBy: [ ] the clock starts

Checks were written before the code and frozen. A step is finished when its checkpoint passes and a second reviewer says so.

Honestly

What it deliberately does not do.

No IAM The runner has unrestricted access to its daemon.
No approvals Anything annotated is provisioned at once.
No locking Two applies could race over one workspace.
No backups The retention window is the only safety net.

It is a proof of a lifecycle, not a platform. The interesting part is the state machine, and that part is finished.
