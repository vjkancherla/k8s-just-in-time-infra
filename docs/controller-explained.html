The controller.

One file. One replica. Four things it listens for.

It turns a Deployment annotation into real infrastructure, keeps that infrastructure alive while something still references it, and removes it when nothing does.

what is here

This controller

Runs after the request. The Deployment is already stored and already applied. It watches events and reacts. If it is down, the Deployment still exists — the pod just waits.

Acts second. Fails open.

Nothing in this repo intercepts an API call: there is no webhook, no ValidatingWebhookConfiguration, no ValidatingAdmissionPolicy. Blocking is the kubelet's job instead — see slide 11.

Its purpose

Make infrastructure live exactly as long as a reference exists.

Reads Deployments carrying a jit.infra/<module> annotation.
Writes InfraClaim objects, Secrets, Services, EndpointSlices.
Calls the runner — the only part that can actually build anything.
Owns the claim state machine and the IP ledger for the whole namespace.

When it runs

Four hooks. That is the whole surface.

on.create + on.update

A Deployment is applied

Anywhere in the cluster, and twice per apply — kopf fires both handlers for one kubectl apply. Ignored unless it carries a jit.infra/ annotation.

timer

Every 30 seconds, per claim

The heartbeat. Runs once at startup too. This is what makes the system self-healing rather than event-dependent.

on.delete

A claim is removed

By TTL expiry, by namespace deletion, or by hand. Hard teardown, no grace period.

on.login

Startup

Connects to the API server with the pod's service account. Nothing else.

Trigger 1 · Deployment applied

Annotation in. Claim, address and container out.

01 Read the annotation Every key starting jit.infra/ becomes one requirement. The suffix is the module name.
02 Create the claim An InfraClaim named {namespace}-{module}, owned by the namespace, holding a teardown finalizer.
03 Allocate an address Ten addresses per namespace, from 172.19.0.100-199, recorded in the jit-ipam ConfigMap.
04 Ask the runner to build POST /v1/runs with the module, the address and the network. Waits up to ten minutes.

Two locks, both in-process. One per namespace, so the read-pick-write of an address cannot be interleaved. One per claim, so kopf's create+update pair cannot drive two applies over one container. Both assume a single controller replica — which is what the manifest sets.

Trigger 1 · the result

The runner builds it. The controller publishes it.

A Outputs come back The module's address, port and URL, read from Terraform state.
B Three objects are written Secret jit-<module>, a headless Service with no selector, and an EndpointSlice pointing at the container's IP.
C The claim turns Ready Status records the endpoint and the Secret name. Its retention clock is cleared.

For Postgres the controller writes the generated password into that Secret itself. It has to: a sensitive Terraform output comes back as the literal text <sensitive>, so the value cannot travel that way.

Trigger 2 · every 30 seconds

The heartbeat that closes the loop.

Re-reads reality and rewrites who references this claim, from the Deployments that actually exist.
Not Ready yet? try provisioning again — unless it already Failed, which is terminal until a Deployment changes.
No references left? the claim goes Orphaned and its clock starts: now + softDeleteTTL, default 30 days.
Clock expired? the claim goes Deleting, the runner destroys the container, the objects are deleted, the IP block is freed.
Two writers, different params? first writer wins; the loser is recorded in a ParamsConflict condition.
Trigger 3 · a claim is deleted

Hard teardown. No clock, no grace.

01 The delete is seen The teardown finalizer holds the claim in place until the work below is done.
02 Destroy the container DELETE /v1/runs/{workspace}. "Destroyed" and "not found" both count as done; anything else is a failure.
03 Delete the three objects Secret, Service and EndpointSlice for that module. A missing one is not an error.
04 Release the address block Drop the finalizer, remove the claim, return the block to the namespace pool.

A destroy that fails is retried every 30 seconds, and on the namespace path the finalizer is still removed — deleting a namespace is deliberate — but it is logged at error level that the container may now leak. A claim already swept by its TTL does not release its block twice; that double release once handed two containers the same address.

What it really is

A state machine with four states and one dead end.

state 1 Pending The claim exists. Nothing is running or nothing is wired up yet.
state 2 Ready The Secret is written. A pod that needs it can now start.
state 3 Orphaned Nothing references it. Still running, on borrowed time.
state 4 Deleting Committed to teardown. Retried every tick until it succeeds.
dead end Failed The runner said no. Stays put until the Deployment changes.

Every arrow between them is drawn by the 30-second timer, not by an event. Delete a Deployment and the claim does not vanish with it — it sits Orphaned, holding the data, until the clock runs out.

What actually blocks a pod

The gate is a missing Secret.

the app's side

It asks for a Secret that is not there yet

The pod references jit-redis with optional: false. The kubelet refuses to start it and reports CreateContainerConfigError.

not an error
—
a wait
the controller's side

It creates the Secret when the infra is real

No init container, no webhook, no status condition to poll. The object's absence is the whole signal, and the kubelet enforces it for free.

That is the design reason there is no admission controller here: blocking before the fact would need a webhook that fails closed, and the project deliberately chose a gate that cannot take the cluster down with it.

Honestly

What it does not do.

One replica Both locks live in the process. A second replica would hand out the same address twice.
No validation Malformed jit.infra JSON becomes an empty set of params, and provisioning goes ahead.
No refusal A second Deployment asking for conflicting params is recorded, not rejected.
No lease The IP ledger is a ConfigMap with no lock of its own; in-process locking is all it has.
No automatic retry A Failed claim needs a Deployment change to try again.
