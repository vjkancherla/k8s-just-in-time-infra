Reviewer model: Muse Spark (independent stage reviewer; did not implement, no stake)
Verdict: BLOCKED

## Blockers

1. **The stage gate's CLEAR conjunct is unsatisfied: `docs/todo.md` ticks Stage H review boxes on CONCERNS verdicts, and no findings file in the range says CLEAR.** `docs/todo.md:122-129` shows S23–S29 as `[x] check - [x] review`, but `docs/reviews/S23-findings.md` … `S29-findings.md` all read `Verdict: CONCERNS`. The plan's completion protocol (`docs/build-plan.md:15-21`) demands a *different model writing CLEAR*, the tracker itself says "`review` is … only the human ticks it" for the frozen-checkpoint review and review means CLEAR (`docs/todo.md:45-46`), and the S29 stage gate restates it: "every stage-H step holds a CLEAR review". The bar was lowered autonomously mid-run — `9b264eb run-overnight: pass on CONCERNS with no blockers (bar is 'no blockers')` — with no ADR and no human directive visible in the repo sanctioning it. The repo's own precedent for accepting CONCERNS is to resolve them by written decision (ADR 0006 did exactly that for S22); no equivalent exists for S23–S29. To be precise about Q4's letter: no *implementation* commit ticked a box — all seven tick commits (`f39fb33`, `5ae9ba7`, `dd49333`, `48b7ee5`, `4c97a6e`, `e928480`, `9e504f8`) are `docs/todo.md`-only — but the boxes assert a review state (CLEAR) that nothing supports. (Side inconsistency: S22's review box stays unticked while S23–S29's are ticked, though S22's CONCERNS were the ones actually resolved by decision in ADR 0006.) Remedy is cheap: an ADR resolving the S23–S29 CONCERNS in place, or fresh CLEAR reviews — but as the tree stands the stage is not done by its own gate, and this is mechanical, so it blocks.

## Concerns

1. **ADR 0016 (import block → `setsubtract`) is the closest design-behaviour call in the stage, and I land it as concern, not blocker, for stated reasons.** The design (`declarers-and-consumers.md:170`) requires a `for_each` import of the initial database; the implementation manages `setsubtract(var.databases, [var.postgres_db])` instead, because OpenTofu evaluates imports at plan time before the same-apply container exists (measured failure on 1.8.1, quoted in the ADR). That is a real behaviour delta: a dropped-out-of-band initial database is never recreated by Terraform (volume is the source of truth). I do not block on it because the specified mechanism is impossible as specified rather than merely inconvenient, the observable contract (in-place additions U2, removals refused U7, destroy U12 — all green on my cold run) is preserved, and the substitution is openly reasoned in an ADR rather than smuggled. The design line itself is still unamended prose, which is the residual debt.
2. **ADR 0020's create-path contract hole: a brand-new claim provisions unvalidated, so an unknown/typo'd key is silently recorded as applied.** Gating `validate_params` behind `provisioned` is rule-3-backed ("create behaviour is unchanged") and is what lets `voting-b`'s pgadmin `http_port:5051` through — but the design table's "unknown key → Refused; tofu only warns" guard now holds only on update. Deliberate and disclosed under "Hard / ruled out"; flagged because a future reader of the mutability table will expect refusal everywhere. (Carried from S29-findings concern 2.)
3. **`patch_applied_params` clears only top-level removed keys, so a dropped nested `settings` key survives in `appliedParams` and the resync re-applies every tick** (`jit-controller/main.py:832-855`; JSON merge patch merges nested objects). Unexercised by the U-table (no settings edit; tenants carry no `settings`), so the gate stays green — the exact container-replace loop ADR 0020 closed one level up, one level down. Latent defect in the v1 mutable surface. (Carried from S29-findings concern 1.)
4. **U13's frozen postgres half asserts nothing: `u13check() { …; [ "$ttl" = "45m" ] || true; … }`.** Only the `voting-b-redis` half is a real assertion of rule 7's TTL maximum. This is frozen S22 shape, not an amendment weakening — none of the 10 amendments touched it — but it means half of U13 can never fail. (Spotted in the `d0d4329..HEAD` diff as unchanged context.)
5. **`docs/build-plan.md:1002` still contradicts the design on the redis declarer, live in the repo.** It says consumers "lose the key (vote: redis…)" / declarers "keep params (…worker: redis + postgres)" — i.e. `vote` consumes and `worker` declares redis — the exact inverse of the design migration table (`:209-213`), the S28 Do (`:1013-1015`), the implementation, the amended S28 checkpoint and the S29 U-table, which all name `vote` declarer / `worker` consumer. ADR 0018 records leaving it stale as orchestrator debt ("correcting it belongs to the orchestrator, not this step"). The implementation is correct; the plan now contains two directly opposing instructions for the same migration, and a reader following the invalidation table would leave redis with no declarer (Pending/AwaitingDeclarer forever). Fix the row; do not re-litigate the migration.
6. **The committed `docs/evidence/S29.log` was captured against a dirty tree** (`# commit 346a9ad`, `# pending 10 uncommitted change(s)` — the controller/runner code and ADRs 0020/0022 landed with the log at `b27f374`). Mitigated, not erased: the S29 reviewer re-ran clean and passed, and I re-ran clean and passed (see Checkpoint assessment). Evidence hygiene only.
7. **Carried S24 runner cluster, still unfixed: workdir leak, silent `state list` skip, prefix-only filter, unlocked delete, stale `runner-api.md`.** Every changed-params POST leaks a ~61MB work dir (`_runs[key]` overwritten without `rmtree`; measured six orphans by the S24 reviewer) — now reachable on *every* Stage H update, so it is unbounded disk growth inside the runner container; a `state list` failure silently degrades to "no `postgresql_*`" and proceeds to the destroy that S24 exists to prevent; the `startswith("postgresql_")` filter misses wrapped addresses; `delete_run` takes no `_run_lock`; `runner-api.md` documents neither the params-keyed cache (the contract S26 depends on) nor the true destroy-params type. ADR 0022 fixed the one that fired (destroy 422 on structured params). The rest is the stage's largest known-unknown surface.
8. **Carried S25 cluster: the `conditions.type` closed enum can silently drop every condition write** (whole-array merge patch + swallowed `ApiException`; one out-of-enum type rejects the array server-side), and the checkpoint leaves `appliedParams={"probe":"s25"}`-style residue on a live claim (neutralised in practice by ADR 0012 item 6's `WATCH_NAMESPACES` confinement, and U11 backfills over it — but the residue defeated the backfill precondition on that claim by construction).
9. **Carried S26 coverage gaps: backfill is live-gated only by U11 (passed cold here), and three behaviours are gated nowhere.** New-declarer-after-a-gap (rule 6), simultaneous fresh disagreeing declarers (rule 3's first-writer-wins is emergent, not implemented — first reconcile sees both and returns before provisioning), and the "consumer adds agreeing params → nothing happens" half of rule 5 have no checkpoint group; ADR 0012's "the implementation's unit tests cover both" is false on its face (`test_declarers.py` imports only the pure helpers, never `reconcile_claim`). The frozen S26 gate is redis-only by design; these live or die in code review, not in any gate.
10. **Carried S27 cluster: double-produced `service_url` (module builds it from the raw password, controller overwrites from the percent-encoded one — the module's value is dead weight kept for the runner-level checkpoint), `service_url_<db>` keys carry the unencoded password by construction (latent `OutputsChanged`/malformed-DSN if a password ever needs encoding; `token_urlsafe` never does today), and `_flatten_outputs_json` rewrites any map output named `service_urls` by magic name collision.** All latent under the current password generator; all worth reconciling before a fourth module arrives.
11. **Post-gate cluster state is not demo-ready, by the gate's own design — re-run `make test-up` before any further gate.** U12 deletes `voting-a`; the EXIT trap restores only `voting-a` annotations/scales (which then point at a deleted namespace) and never voting-b's `vote` redis annotation, which U13 demotes to consumer (S29-findings Notes). My cold gate run ends in exactly this state. Not a defect (U12 must destroy), but the next runner must know the gate consumes its own stack.
12. **`make test-up` exits non-zero on a cold host for reasons outside Stage H — do not misattribute.** `voting-a` verifies 17/17 cold (observed in `docs/evidence/test-up.log:494`); the trailing `voting-b` verify fails R2/R6/R8 because `app/scripts/verify.sh` hardcodes `VOTE_URL=https://vote.localhost:8082` (voting-a's Ingress) while reading voting-b's redis — posts land in voting-a, voting-b's LLEN stays 0→0. Pre-existing app/verify behaviour, no `app/` file in this stage's range, correctly out of the S29 gate's scope (it runs `NS=voting-a` only). Recorded so the red `test-up` exit is not read as a Stage H regression.
