Delete the app. A clock starts.

The container keeps running. Redeploy inside the window and nothing was ever destroyed — same container, same data, same IP. Let the clock run out and it goes, data and all. Delete the whole namespace and there is no window at all.

Accidents get a grace period. Decisions do not.

On expiry — the sweep, in order

  1. The runner destroys the container and its volume
  2. Secret, Service and EndpointSlice are deleted
  3. The IP address returns to the IPAM pool
  4. The finalizer is removed and the InfraClaim is deleted

The clock starts late, never early: expiresAt is set on the first resync that notices the Deployment is gone, not at the moment Kubernetes deleted it. If the controller is down, the infra simply lives longer than expected. That is the safe direction to be wrong in.

Two ways in, two speeds

Both roads end at the same destroy. They differ in whether a clock gets a say.

slow · soft delete

The Deployment is deleted

  • Routine — every rollout, every image change, every scale event
  • The claim survives: it is owned by the Namespace, not the Deployment
  • No references left → claim goes Orphaned, the clock starts
  • Redeploy inside the window → back to Ready, nothing reprovisioned
  • Window runs out → destroyed
fast · hard delete

The Namespace is deleted

  • Deliberate — someone removed a whole environment
  • Kubernetes GC deletes every namespaced resource
  • The finalizer intercepts each InfraClaim instead
  • expiresAt is never consulted — the clock is irrelevant
  • Destroyed now

How the controller knows

It does not watch for delete events and it does not sleep until expiry. Every InfraClaim gets a 30-second timer, and each tick re-derives the truth from what is actually in the cluster.

# jit-controller/main.py
@kopf.timer("jit.io", "v1alpha1", "infraclaims", interval=30, initial_delay=True)
def resync_referenced_by(body, namespace, name, logger, **kwargs):
    """Periodic resync: recompute referencedBy, handle orphaning and TTL sweep."""

Each tick: list the live Deployments referencing this module, fresh-read the claim's status from the API server (the kopf body can lag the controller's own patches), then decide.

References exist?Current phaseWhat the tick does
Yesnot Ready, not FailedTry provisioning — call the runner
YesReadyUpdate referencedBy, clear expiresAt
YesFailedLog and skip — Failed is terminal until the Deployment changes
Nonot OrphanedMark Orphaned, set expiresAt = now + TTL
NoOrphanedCompare now against expiresAt; if past it, sweep
NoDeletingRetry the destroy — a previous attempt failed

The expiry test is a plain datetime comparison on each tick. There is no scheduled callback and no watch event for expiry; 30-second granularity is fine when the shortest window in testing is two minutes.

The finalizer: why cleanup cannot be skipped

Every InfraClaim carries the finalizer jit.infra/teardown. Kubernetes refuses to remove the object until the controller takes it off — and the controller only takes it off after a destroy has succeeded.

The consequence is the point: the controller gets its turn even if it was down when the delete was requested. The object waits in Terminating until it comes back.

The double-release guard

Both paths release the IP block, and the same claim can reach both: the sweep removes the finalizer, the object is deleted, and that deletion fires on.delete a second time. The guard is one check on the claim's phase.

phase = (body.get("status", {}) or {}).get("phase", "")
if phase == "Deleting":
    logger.info(f"Claim {name} was already swept; not releasing its IP block twice")
else:
    release_block(namespace)

When the runner is down

The destroy fails, so the finalizer is never removed, so Kubernetes never finishes the deletion. The claim stays Terminating; a namespace deletion leaves the namespace Terminating too.

destroy fails
runner unreachable
→
finalizer stays
cleanup is not skipped
→
retried every 30s
phase Deleting
→
runner returns
next tick succeeds
It stalls visibly rather than leaking quietly. That is deliberate: the system would rather stop and be noticed than forget a container exists. The cost is a namespace stuck in Terminating until someone acts.

The manual escape hatch, in order:

# 1. destroy the infra by hand
tofu destroy -auto-approve ...

# 2. patch the finalizer off
kubectl patch infraclaim voting-a-redis -n voting-a --type=json \
  -p='[{"op":"replace","path":"/metadata/finalizers","value":[]}]'

# 3. clean up the IPAM ledger
kubectl get configmap jit-ipam -n default -o json \
  | jq --arg ns 'voting-a' '.data.allocations |= (fromjson | del(.[$ns]) | tojson)' \
  | kubectl replace -f -

Expiry: the clock runs out

When now passes expiresAt, the sweep runs in this order.

  1. The runner is called: DELETE /v1/runs/{namespace}, with the module name
  2. The runner runs tofu destroy -auto-approve — container and volume removed
  3. The controller removes the Secret, the Service and the EndpointSlice
  4. The IP address returns to the IPAM pool
  5. The finalizer is removed and the InfraClaim is deleted
Afterwards the namespace looks as if the infra was never there. MinIO state objects live outside the cluster and survive — make jit-down clears those.
If the runner is down at expiry: the destroy fails, the finalizer stays, and the controller retries on the next tick. See When the runner is down.

Hard delete: the Namespace goes

Deliberate. Someone went out of their way to remove an entire environment, so there is nothing accidental to protect and no clock to consult.

kubectl delete namespace voting-a
# or: make ns-delete NS=voting-a
  1. Kubernetes marks the Namespace for deletion — it enters Terminating
  2. Garbage collection marks every namespaced resource, Deployments and InfraClaims alike. The claims carry a finalizer, so their removal is blocked
  3. The finalizer intercepts each claim and the delete handler fires. It does not look at expiresAt — the clock is irrelevant here
  4. The controller calls the runner once per module: DELETE /v1/runs/voting-a/<module>
  5. The runner runs tofu destroy -auto-approve — container and volume removed
  6. The controller removes the Secret, the Service and the EndpointSlice, where GC has not already done it
  7. Each claim's address returns to the IPAM pool; when the namespace's last claim is released, the whole block is freed
  8. The finalizer comes off, the InfraClaims are deleted, and the Namespace completes its deletion

What is left afterwards

the namespacegone
the containersgone
the IP blockfree again
MinIO state objectsoutside the cluster; jit-down clears them

The other namespace

voting-b claimsstill Ready
voting-b containersstill running

Nothing at all — J8 in the verification suite exists to prove exactly this.
Runner down on this path? The finalizer cannot complete, so the namespace stays Terminating and the controller retries each tick. Same escape hatch as the other path.
