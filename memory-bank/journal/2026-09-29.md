# 2026-09-29 - the overnight run: Stage H built autonomously, and what it exposed

Companion to `memory-bank/activeContext.md`. Durable rules live in `docs/lessons.md`;
each step's record is `docs/reviews/S<NN>-findings.md`, the tracker is `docs/todo.md`,
and the run's own record is `docs/evidence/overnight-20260929T001629Z.{md,log}`.

## What was asked

Drive every outstanding Stage-H item (S23-S29) overnight with no manual intervention: an
orchestrator spawns an implementer, then a different-model reviewer, loops until there are
no blockers, and keeps the MacBook awake.

## Which orchestrator

Three options were weighed: **gnhf** (a tested Ralph loop, OpenCode-native), **firstmate**
(a parallel task-fleet distro) and a purpose-built shell script. firstmate was rejected - it
parallelises independent tasks and keeps a human "captain" for decisions, neither of which
fits a dependent, gated plan. gnhf was trialled live: it drives `opencode serve` correctly,
but its per-iteration contract demands a strict JSON final message and, on the first heavy
objective (the whole of S23), the worker never produced one - `StructuredOutputError` then
"OpenCode produced no final answer". It was parked and the shell script kept, because the
script gates on artefacts (`PASS` in `docs/evidence/SNN.log`, the findings verdict) rather
than on the model's word, and because the plan's "one step per session" maps onto a fresh
`opencode run` per role.

## S23: the measured verdict, the human override, and the arms race

The spike measured honestly: redis and postgres replaces <=1s, 50 of 50 queued votes lost
across a redis replace, vote/worker reconnected, `call_runner` off-loaded by kopf. On the
design's criterion 1 ("adds or tunes, never removes data") that is `VERDICT: maxmemory
refused` - the v2 fork the build plan reserves for a human.

The human overruled it: an annotation-driven change is *explicit approval for downtime*, so
`maxmemory` stays mutable. Writing that verdict by hand while keeping the measured log made
the reviewer block - correctly: the checkpoint "confirms the paperwork, not the
measurement", and after a first checkpoint amendment it mutated the tree (stubbed the probe)
and showed the amended gate still passed. Two checkpoints were amended and two ADRs written
before the loop was stopped; the real fix was policy, not another grep. The run was reset to
`4fd26b9`, the decision recorded as one ADR (**0007**, `maxmemory` mutable, downtime
accepted), the checkpoint left untouched, and a review-prompt note told the reviewer to judge
the ADR as the approval rather than re-derive it. That attempt returned CONCERNS, no blockers.

## The criterion fix

The script had required a literal `CLEAR`; the reviewer naturally returns CONCERNS with no
blockers. That is the intended bar here ("no blockers"), so the gate was changed to pass on
CLEAR **or** CONCERNS with an empty Blockers section (`scripts/run-overnight.sh`). S23 was
ticked on that basis, and the overnight run then covered S24-S29.

## The overnight run

`STEPS="24 25 26 27 28 29"`, `MAX_ATTEMPTS=3`, `ON_EXHAUST=continue`, under `caffeinate`.
S24 and S26 came back BLOCKED and were repaired in-loop; every step ended CONCERNS with no
blockers and was ticked. Exit 0 at 07:56, 49 commits, tree clean. The stage gate is green in
`docs/evidence/S29.log`: U1-U13 live, `make jit-verify` J1-J11 PASS, `make verify` 17 PASS.

## Left open - and the thing to judge

The run wrote **15 ADRs (0008-0022), 10 of them checkpoint amendments**, and changed 6
frozen checkpoints (S24-S29, +174/-67). Every amendment has an ADR and was reviewed, so the
retained protocol was followed - but the volume is exactly what the frozen-checkpoint rule
exists to limit, and some amendments reword an assertion to fit the code. Stage H is ticked
but **not accepted**: the RUNBOOK stage boundary (cold teardown, cumulative review by the
strongest model, then read one file yourself) has not run. `S22`'s review box also remains
unticked. All S23-S29 verdicts are CONCERNS, never CLEAR, so the tracker is green on a
looser bar than `docs/build-plan.md` states.

## The stage review, and the decision that closes it

A cumulative stage review by an independent model (Muse Spark) that did neither the
implementation nor the per-step reviews returned **BLOCKED - on process, not code**. The one
blocker: the tracker ticked S23-S29 `review` boxes on CONCERNS while `docs/build-plan.md`
requires a literal CLEAR, and no recorded decision sanctioned the looser bar. Otherwise it
was a clean bill: all ten checkpoint amendments fix genuine harness/contract bugs and several
strengthen the gate; the cold S29 gate passed (U1-U13 + 17 R + J1-J11); ADR 0007 is sound. It
raised twelve concerns, ranked by attack value - the runner workdir leak and the `state rm`
silent-skip first.

**ADR 0023** closes it the way the repo's precedent (ADR 0006) does: it records the human's
"no blockers" direction, ticks S22's review box (whose findings already said CLEAR), corrects
the inverted redis-declarer row at `build-plan.md:1002`, and accepts the twelve concerns as
recorded debt with the reviewer's ranking. The lesson, which belongs in `docs/lessons.md` on
the next rework: lowering the verdict a gate accepts is an ADR decision, not a script tweak.
