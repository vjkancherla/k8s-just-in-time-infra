# 2026-09-15 — the timeline question, and the console brought under a gate

## What was asked

Whether the creation of a Deployment, the controller's reaction, the runner and the module
containers could be visualised; how hard it would be. Two designs were on the table: a
retrospective timeline assembled from timestamps that already exist, and a live four-lane
view driven by a stream (`kubectl get events -w` plus `docker events`).

## What the evidence said

A 65-line read-only probe (`/tmp/timeline_probe.py`, not committed) reconstructed a real
run from three sources — `kubectl get -o json`, `docker inspect`, and the two logs
(`kubectl logs --timestamps` for the controller, `docker logs --timestamps` for the
runner). Today's warm run, t0 = the first Deployment applied:

Two premises were corrected against the code and the cluster:

- **No phase timestamp exists.** All three claims report `"conditions": []` and
  `set_condition()` is only ever called for `ParamsConflict` (main.py:650). `Pending`/`Ready`
  are plain phase patches. The Ready moment survives only in the controller's log.
- **kopf does not post handler log lines as events.** `PostingSettings(enabled=True,
  loggers=False)` in kopf 1.44.6. It posts its own `Handler 'x' succeeded.` /
  `All handlers succeeded.` on outcome only, and events expire in about an hour. So the
  live design needs explicit `kopf.info()` calls in the controller, not just a subscriber.

## What was decided

- Build the retrospective timeline (A) first: retrospective, no controller change, and
  every timestamp already recorded. The live view is S22 if A is not enough.
- The timeline is a **read model** (`scripts/timeline.sh`) behind `make timeline`, not a key
  in `make state` — `make state` is polled every two seconds and the timeline reads a log.
- The console's ad-hoc work gets a paper trail: **S19** (the page), **S20** (the proxy),
  **S21** (the timeline). S19/S20 are retro-checkpoints, written from the Goal and run
  against the code as it stands.
