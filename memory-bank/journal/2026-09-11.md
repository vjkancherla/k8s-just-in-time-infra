## Confirmed defect — the resync retry path leaks the IP block

`jit-controller/main.py` releases a swept claim's block in exactly one place on the TTL path:
line 896, inside the `exp` branch, only when `destroy_infra` returned true. The **retry** branch
(lines 841-849) destroys, cleans up and deletes the claim, and calls no release at all. The delete
handler then deliberately skips its own release, because `phase == "Deleting"` (line 942). So when
the first sweep attempt fails — the runner is down, which is exactly what J10 rehearses — and a
later tick retries successfully, **nothing releases the block**.

Probe: `docs/evidence/leak-probe2.sh`, log `docs/evidence/leak-probe2.log`. One namespace (`hatch-leak`), one redis
claim, 2m TTL, runner stopped past the expiry and held down through two failed retries, then
restarted. Claim gone, container gone, ledger entry surviving:

```
[09:44:55] WARNING Destroy retry failed for hatch-leak-redis, will retry next tick
[09:45:29] WARNING Destroy retry failed for hatch-leak-redis, will retry next tick
[09:46:09] INFO Claim hatch-leak-redis was already swept; not releasing its IP block twice
claim present: no · container present: no
LEDGER AFTER: {"hatch-leak": {"offset": 0, "base_ip": "172.19.0.100", "count": 1}}
```

Impact: one of the ten blocks in 172.19.0.100-199 is lost per occurrence, silently and permanently.
The direction is exhaustion ("No IP block available for namespace ..., <claim> left unprovisioned"),
not duplicate addresses. It compounds, because the entry keeps its `offset`: a namespace of the same
name re-created later resumes the same block with a count that still includes the dead claim.

Fix (recommended, not yet applied): call `release_block(namespace)` in the retry branch after
`remove_finalizer_and_delete` — it cannot double-release, since that branch only runs when the
TTL-path release did not.

**v1 of this probe gave a false all-clear, and the reason matters.** `docs/evidence/leak-probe.sh` restarted
the runner as soon as the phase went `Deleting`; the sweep's in-flight destroy then *succeeded*
(09:39:26 → 09:39:36), so the sweep released the block itself at line 896 and the guard correctly
skipped the handler. It looked like a pass while testing nothing. Read the probe log against the
controller log before believing either.

## Confirmed defect — the README escape hatch fails for pgAdmin

S17's "Do" list names the wedged-finalizer escape hatch, and the design note's failure mode 3 is
"destroy fails → escape hatch documented". `README.md` step 2 lists the variables to pass and
mentions `-var http_port` and `-var postgres_password` for pgadmin — but not `postgres_url`, which
`jit-modules/modules/pgadmin/variables.tf` line 36 requires with no default. Executed in a scratch
copy of the module (local backend override, so no search state was touched):

```
$ tofu destroy -auto-approve -input=false -var name=probe -var ip=172.19.0.199 \
    -var network=k3d-voting-app -var postgres_password=x
Error: No value for required variable

```

This is the same error the controller had to route around in `destroy_infra` (main.py:699). The
hatch is most likely to be needed *for* pgAdmin, because that is the module whose destroy depends on
the postgres Secret. Doc-only fix, so it does not invalidate the checkpoint.

## Latent, not reproduced

- **The ledger has no lock.** `ipam.py` does a bare read-modify-write of the single `jit-ipam`
  ConfigMap in both `allocate_block` and `release_block`, and `namespace_lock` is keyed **per
  namespace** — so it serialises claims within one namespace and cannot serialise two namespaces
  against each other. Neither release path (896, 945) takes any lock. Two namespaces allocating
  concurrently can both read `{}` and both be handed offset 0, which is the J1 symptom one level up.
  Tried and failed to reproduce: `docs/evidence/block-race-test.sh` applied `overlays/voting-a` and
  `overlays/voting-b` back to back from a clean ledger, twice; voting-a took offset 0 and voting-b
  offset 1 both times, six distinct addresses (`docs/evidence/block-race.log`). Two attempts is not proof of
  absence, and this is the README's own documented first-run sequence. Fix: one lock in `ipam.py`
  around each read-modify-write.
- **`_allocated_ip` cannot tell "read failed" from "no address".** It returns `""` on any
  `ApiException` (main.py:154-160) and `""` is exactly the signal `ensure_claim` uses for "this claim
  has no address yet". A transient GET failure therefore takes the allocation path for a claim that
  already has one: the count increments again and `first_free_address` may pick a different address,
  which is written to `status.allocatedIP` while the container keeps the old one. J1's
  container-IP-matches-status assertion would catch it during a suite run.
- **`jit-down` leaves the ledger unreconciled.** `jit-ipam` is created and patched only by the
  controller: it is not in `deploy/controller.yaml`, and neither `scripts/jit-up.sh` nor
  `scripts/jit-down.sh` mentions it. So the ledger survives a stack bounce, and combined with the
  first defect a `make jit-down` → `make jit-up` cycle can start from a count that no longer matches
  reality. Not tested end to end (it means tearing the stack down and back up).

## The fix, and the checkpoint that now describes the tree

Applied the prescribed fix and proved it before spending another 25 minutes on the gate.

`jit-controller/main.py`:

- `remove_finalizer_and_delete` now returns whether the claim is gone (a 404 counts as gone — the desired
  state, not a failure). Both teardown exits gate their release on it, so the release and the claim's
  removal move together: releasing before the removal would double-release on the next tick, and never
  releasing it is the leak.
- The resync retry branch releases, having destroyed, cleaned up and deleted the claim.

Executed, not reasoned: `docs/evidence/leak-probe3.sh` (v2's body, so the two logs are comparable) against
the reloaded controller. `LEDGER AFTER: {"voting-a": {"offset": 0, "base_ip": "172.19.0.100", "count": 3}}`
— no `hatch-leak`. The controller log (`docs/evidence/leak-probe3-controller.log`) shows the order that
makes it exactly-once:

```
10:13:40 INFO  Resync hatch-leak-redis: retrying destroy (Deleting)
10:13:45 INFO  Destroy response for hatch-leak/redis: destroyed
10:13:45 INFO  Deleted claim hatch-leak-redis after TTL expiry
10:13:45 INFO  Released IP block for namespace hatch-leak          <- jit-ipam, after the claim is gone
10:13:45 INFO  Hard delete triggered for hatch-leak-redis ...      <- the delete handler, too late
10:13:50 INFO  Claim hatch-leak-redis was already swept; not releasing its IP block twice
10:14:50 INFO  Hard delete triggered for hatch-leak-redis ...      <- kopf delivers it a second time
10:14:54 INFO  Claim hatch-leak-redis was already swept; not releasing its IP block twice
```

Those last lines are why the release stayed in the `Deleting` paths instead of moving into the delete
handler: the handler runs **twice** for one claim, so a handler-owned release would have decremented the
namespace twice. The phase guard absorbs both. Moving the release there would have looked tidier and been
wrong.

`README.md`: the escape hatch's step 2 now lists what each module actually requires — `postgres_password`
for postgres and pgadmin, `postgres_url` for pgadmin, both without a default, taken from the `jit-postgres`
Secret (`POSTGRES_PASSWORD`, `address`, `port`) — plus `http_port` only when it is not the module's 5050.

Then the gate, on the fixed tree: `bash scripts/checks/S17.sh` exit 0 — `PASS: J1-J11 all PASS in
.workflow/verify-jit.md`, `PASS: ===== 17 PASS, 0 FAIL ===== in voting-a`, `PASS: S17 - two namespaces,
J1-J11 and the R-checks both green` (`docs/evidence/s17-run-postfix.log`,
`docs/evidence/verify-jit-postfix.md`). Environment back where the checkpoint expects it: voting-a on three

Acted on three, recorded two, and the acting found something the review had not:

5. **Tenant visibility of an `Orphaned` claim — still open, by design.** The design note already lists it

## Running the concerns found two more defects

The three fixes above were proven by running them, and the running paid for itself.

**`jit-down` raced its own claims.** Step 1 deletes the InfraClaims with `--wait=false` and the script
then removes the runner — the very thing those deletes need, because the controller's delete handler is
what destroys the containers. The first bounce run got away with it; the second did not: the three claims
sat Terminating for the whole two-minute window and came back on the next `jit-up` as *Ready* with no
container behind them. Ready is exactly what the controller checks before provisioning, so the tenant was
never re-provisioned — `containers up: 0 of 3`, R2 FAIL, the app dead, and no error anywhere saying so.
Kept as `docs/evidence/s17-jitdown-bounce-race.log`. The script's own header had claimed the right order
("torn down *first*, while the runner is still up"); it simply never waited. Fixed with a bounded wait for
the claims to disappear plus a loud warning if they will not, and re-run green
(`docs/evidence/s17-jitdown-bounce.log`).

Note what made the race visible: the failing run was the *second* one. A single green bounce proves
nothing about a race — the same lesson as leak-probe v1 versus v2, learned again from the other end.

**An unguarded array read in the R-checks.** The wedged run's report carried
`./scripts/verify.sh: line 88: OPTS[0]: unbound variable` where R2's own guarded message belonged: R1
could not parse the vote page, so `mapfile` left `OPTS` empty and every `${OPTS[0]}` tripped `set -u`.
Worse, `grep -q "${OPTS[0]}"` on an empty name matches *any* line, so R5's two label assertions could pass
vacuously on a dead app — the silent-empty pattern the S16 review raised, in the file S16 reworked. `OPTS`
is padded to two slots and R5 now requires them non-empty. Verified both ways: against a dead app,
`10 PASS, 7 FAIL` with no shell noise and R5 failing honestly
(`docs/evidence/s17-rchecks-negative-options.log`); against the live app, `17 PASS, 0 FAIL`.

## The cold start, after the decision: three traps fixed, one question open

The review's concern 4 was "the cold `make destroy` was never exercised". Running it, with the namespace
decision made (tenants never in `default`), produced this, in order:

1. `make destroy` takes the cluster *and its containerd*: `jit-controller:latest` was in `docker images`
   and nowhere else, so `make jit-up` waited 180s to fail on ImagePullBackOff. `jit-up.sh` now asks
   kubelet what the cluster holds and imports when the answer is no (16s, exit 0).
2. `jit-down` — the fix from the same day — died on a cluster with no CRD: `kubectl get infraclaims | wc -l`
   under `set -euo pipefail`, where kubectl's failure became the pipeline's, and `set -e` killed the script
   just before the sweep that removes the module containers. Guarded now; the cold run is what found it.
3. A bare `make all` deployed the app into `default`, whose Ingress claimed `vote.localhost`, and the
   J-suite's PREREQ then refused to run — correctly, "one namespace per demo host". That is the collision
   the decision above settles; `app/Makefile` now defaults `NS`/`KUSTOMIZE_DIR` to the `voting-a` overlay.

With those in place the recipe reaches provisioning — three claims Ready, vote rolled out — and stops at
the real blocker: `init-db` **`FATAL: password authentication failed for user "postgres"`**. The postgres
data volume outlives the container (`jit-down` and `clean-slate` use `docker rm -f`, which is not a
`tofu destroy`), while the controller writes a fresh password into `jit-postgres` for the new stack.
Postgres ignores `POSTGRES_PASSWORD` on a data directory that already exists, so the container is up, the
Secret is right, and the app can never authenticate. `docker volume ls` lists
`voting-a-postgres-postgres-data` and a `default-...` one from the earlier `default` experiment.

That is a design question, not a defect to patch: on a bounce or a cold start, either the data volume goes
with its container or the password has to be persisted rather than regenerated. Left for the human, with
the evidence committed (`docs/evidence/s17-cold-path.log`).

The demo itself was restored by hand after the runs disturbed it — `clean-slate.sh` (which does remove the
volumes), redeploy the `voting-a` overlay, restart the three app Deployments so they pick up the new
Secrets. Final state: three claims Ready, ledger `{"voting-a": {"offset": 0, "count": 3}}`, three pods
`1/1` Running.





## S17 closed: the cold start runs green, and the volume question was already answered

The review's concern 4 came back as **closed, and it was the right concern**. Running the cold path for real
turned the last open item into five defects. Four were fixed earlier (the controller-image import, the
`jit-down` wait surviving a cluster with no CRD, the `voting-a` pin, and the container sweep that removes the
leftovers a cluster delete strands). The fifth is the one the third run stopped at, and it had been recorded
as a design question: *on a bounce or a cold start, either the Postgres data volume goes with its container or
the password has to be persisted instead of regenerated.*

Reading rather than choosing settled it. The code had already answered:

- `scripts/verify-jit.sh`'s J6 comment says it outright: "The data volume belongs to the module, so the
  destroy takes it with the container: a re-created Postgres must initdb fresh rather than come back holding
  a database whose password the controller has already forgotten."
- Every recorded J6 run reports `postgres data volume removed` — the runner's `tofu destroy` destroys the
  `docker_volume` resource alongside the container.
- `jit-modules/modules/postgres/main.tf` forbids the alternative in a comment: "Do not add a `random_password`
  resource that replaces `var.postgres_password`".
- `scripts/checks/S04.sh` requires the volume to survive only a *targeted* `docker_container` destroy, and
  destroys the volume itself in the next step.

So the rule was never in doubt: **a container removal takes its volume.** What broke it was
`scripts/jit-down.sh` step 2 — the fallback sweep that removes leftover module containers *by name*, which
runs exactly when the destroy cannot (no CRD, no state, no Secret: the state that made the run cold). It left
the volume behind, and the next stack wrote a fresh password into a data directory that still held the old
one, so `init-db` died on `FATAL: password authentication failed for user "postgres"`. Step 2 now removes
`<container>-data` with the container.

The rejected option was weak on its own terms: persisting the password could not have rescued the volume that
already existed, because that password lives inside the data directory and nowhere else. Any password-owning
design needed a volume reset anyway, so the simpler rule wins.

Evidence: `docs/evidence/s17-cold-path-green.log` — both summaries green (`17 PASS, 0 FAIL` then
`11 PASS, 0 FAIL`), and step 3 shows the fix in one line: `jit-volumes=[voting-a-postgres-postgres-data ]`
before `make jit-down`, `jit-volumes=[]` after. `docs/evidence/s17-final-gate.log` is the gate re-run on the
final code; its last PASS line is reachable only under `set -euo pipefail` if everything above it passed. The
demo was rebuilt by that same cold run and is healthy: three claims Ready, ledger
`{"voting-a": {"offset": 0, "count": 3}}`, three pods 1/1.

Still the human's, and nothing else: the review boxes. All 18 remain unticked, S17's included.
