## Defects found, and the evidence
1. **pgadmin never registered its server.** The daemon could not see the runner's `/tmp`, so Docker
   created an *empty directory* at `/pgadmin4/servers.json`; nothing read it, so nothing failed for
   eleven steps. Fixed with a directory both sides see (`$HOME/.jit-host-share` +
   `TF_VAR_share_dir`).
2. **`jit-pgadmin` advertised port 6379** (the S16 flag): pgadmin exports no `port` output. Now
   `port = 80`, and the controller re-states the Service spec on 409.
3. **pgadmin's destroy needed `postgres_url`** after postgres's Secret was cleaned up in the same
   sweep → "No value for required variable" → a claim stuck in `Deleting`. Placeholder fallback.
4. **The runner's destroy resolved to the wrong module.** The TTL sweep destroys a claim and kopf's
   delete handler destroys it again; on that second call the cache no longer held postgres, the
   fallback took "the workspace's only cached run" - redis - and removed
   `voting-a-redis-redis`, a live, referenced container. Fixed: an explicit module always wins
   (S06/S07 send no module and keep the fallback). The runner also had no logger at all; it has one.
5. **`deploy/minio.sh` 409 on an existing bucket** - `make jit-up` was not re-runnable.
6. **`release_block` ran twice per swept claim** (sweep + delete handler) - ledger drift.
7. **`verify.sh` R14/R15 were unscoped**, so they read whichever namespace the context pointed at.

## Closed the same day — S17 done

Commit range `a82a6a9..e00a179` (seven commits). Checkpoint `bash scripts/checks/S17.sh` → exit 0,
ending `PASS: J1-J11 all PASS`, `PASS: ===== 17 PASS, 0 FAIL ===== in voting-a`,
`PASS: S17 - two namespaces, J1-J11 and the R-checks both green`. Evidence: `docs/evidence/s17-run.log`
(copy `docs/evidence/s17-green-run.log`), suite report `docs/evidence/verify-jit-green.md`.

**The J1 duplicate address had two causes, not one.** Both are in `jit-controller/main.py`:

- `ensure_claim` read this claim's address, read the other claims' addresses, picked the first free
  one, then patched — four non-atomic steps. `claim_lock` is keyed per claim and taken *after*
  `ensure_claim`, so it serialised provisioning and never allocation between different claims.
  kopf fires `on.create` **and** `on.update` for one Deployment apply, each iterating every claim,
  so the interleaving is the normal case. Fixed with `namespace_lock(ns)` around the whole
  read-pick-patch. The earlier note in this file guessed at `ensure_claim` and was right about the
  window — but the missing lock was the cause, not a second call for one claim.
- `release_block` ran twice for a swept claim: the TTL sweep releases it, and removing the finalizer
  then deletes the object, which fires the delete handler and releases it again. The namespace's
  `count` reached zero while claims still held addresses, so the block was free to be re-issued.
  `handle_claim_delete` skips the release for a claim already in phase `Deleting`. **This is the
  `count: 2` against 3 live claims that the ledger showed** — it was a real defect, not just
  confusing arithmetic.

Evidence that it is fixed rather than lucky: `docs/evidence/race-test.sh`, three clean-slate `voting-a`
deploys each requiring three distinct IPs **and** `count: 3` → **3/3 OK** (`docs/evidence/race-test.log`).
The suite itself then deployed `voting-a` with `.100/.101/.102` on both of its complete runs.
A single green run cannot distinguish a fixed race from a lucky one, which is why this exists.

**J11 was unreachable, and had two defects.** The first complete run failed it:
`docs/evidence/s17-run-j11fail.log` — the SigV4 list signed the prefix as `ns/`, but a canonical query string
requires `ns%2F`, so MinIO answered **403 SignatureDoesNotMatch** (`safe="/"` → `safe=""`). The
second complete run passed J11 and *still* failed the gate: `docs/evidence/s17-run-j11-nopass.log` shows
`10 PASS, 0 FAIL` and `FAIL: J11 did not report PASS`, because every J11 assertion is negative (a
`fail` with no matching `pass`), so a passing J11 printed nothing at all. Both are why the
checkpoint asserts the `^J11 PASS` line and not merely the exit code.

The gate's exit code alone called both of those runs fine. It was the PASS line that caught them.
